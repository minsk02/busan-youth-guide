# 요구사항명세서 초안

버전 0.1 · 2026-10-25 · 상태 팀 검토 및 데이터 검증 전

교수님 SRS 템플릿에 옮길 협업용 초안이다. 아래 우선순위와 수치 목표는 제안이며 합의 또는 측정 결과가 아니다. 사용자 유형·구체적 테스트 입력은 팀원 3이 검토한다.

## 목적과 범위

부산 청년 대상 프로그램을 자연어로 검색하고 조건에 따라 추천·비교하는 웹 서비스의 동작을 정의한다. 일반 사용자는 로그인 없이 검색한다. 프로그램 신청은 외부 공식 페이지에서 하며 시스템이 신청이나 예약을 대행하지 않는다.

## 대상과 운영 환경

주요 사용자는 부산의 프로그램 참여 기회를 찾는 청년이다. Chrome·Edge의 데스크톱 웹을 초기 대상으로 제안한다. 사용자 계정과 관리자 화면은 초기 범위에 포함하지 않는다. 데이터 수집은 운영 스크립트 또는 서버 작업이 수행할 예정이며 별도 사용자 액터로 가정하지 않는다.

프레임워크, LLM 제공자·모델, DB는 미정이다. SQL 등 구조화 검색으로 시작할 수 있으며 벡터 DB는 필수 구성요소가 아니다. 최종 기술 선택은 실제 응답과 팀의 기술 경험을 확인한 후 기록한다.

## 제약과 의존성

외부 데이터 및 AI API의 사용 권한·이용조건·비용·호출 제한에 의존한다. API 키는 서버 측에서 사용한다. 원본 필드가 없는 조건은 지원한다고 가정하지 않는다. 조건 충족과 참가 자격 확정을 구분하며, 사용자의 최종 신청 판단을 대신하지 않는다.

## 기능 요구사항

Must는 초기 필수 범위 제안이다. 데이터 의존 요구사항은 검증 후 범위와 표현을 조정한다.

| ID | 이름 | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---|---|---|
| FR-001 | 자연어 조건 추출 | 시스템은 사용자 질문에서 지원하는 검색 조건을 구조화하고 적용한 조건을 표시해야 한다. | Must | 승인된 테스트 질문에서 기대 조건과 추출 결과 비교 |
| FR-002 | 실제 데이터 검색 | 시스템은 검증된 데이터 저장소에서 추출 조건에 부합하는 후보를 검색해야 한다. | Must | 통제 데이터에서 기대 ID 집합과 결과 비교 |
| FR-003 | 조건 기반 추천 | 시스템은 후보를 확인 가능한 조건으로 정렬하고 각 추천의 일치 근거와 미상 조건을 표시해야 한다. | Must | 근거가 원본 또는 명시된 파생 규칙과 일치하고 미상 조건을 충족으로 계산하지 않음 |
| FR-004 | 프로그램 비교 | 시스템은 사용자가 선택한 2~3개 프로그램의 공통 비교 항목을 나란히 표시해야 한다. | Must | 선택한 ID의 확인된 값만 표시하고 누락값은 확인 불가로 표시 |
| FR-005 | 상세와 출처 | 시스템은 상세 정보에 원본 기반 값, 데이터 출처 링크, 실제 수집 시점을 표시해야 한다. | Must | 테스트 결과의 출처·수집 시점 표시 확인, 개별 공식 링크는 있을 때만 표시 |
| FR-006 | 검색 결과 없음 | 시스템은 결과가 없으면 조건 완화를 제안하고, 사용자의 확인 없이 조건을 변경하지 않아야 한다. | Must | 0건 조건에서 임의 결과를 생성하지 않음 |
| FR-007 | 날짜와 모집 상태 | 시스템은 신청기간·모집 상태가 명확한 경우에만 모집 여부를 판정하고 불명확하면 미상으로 표시해야 한다. | Must | 마감 전·후·당일·상시·잘못된 날짜의 사전 정의 결과와 비교 |
| FR-008 | 데이터 수집 | 시스템은 허용된 외부 데이터에서 검증된 레코드를 수집하고 수집 시점을 기록해야 한다. | Must | 중복 수집·외부 오류에서 기존 유효 데이터 보존 및 오류 기록 확인 |

## 비기능 요구사항

| ID | 영역 | 요구사항 | 우선순위 | 검증 기준 |
|---|---|---|---|---|
| NFR-001 | 장애 처리 | 시스템은 외부 호출에 타임아웃을 적용하고 실패 시 사용자에게 실패 상태를 안내해야 한다. | Must | 타임아웃 주입 시 무한 대기 없이 오류 안내, 제한값은 구현 전 확정 |
| NFR-002 | 비밀정보 | 시스템은 API 키를 서버 환경변수에서 읽고 브라우저 응답·저장소·로그에 포함하지 않아야 한다. | Must | 설정·응답·로그 검토 |
| NFR-003 | 개인정보 | 시스템은 초기 범위에서 실명·연락처·정확한 위치를 요구하지 않고 원문 질의를 기본 영구 저장하지 않아야 한다. | Must | 화면·DB·로그 확인, AI 제공자 전송·보관 조건은 별도 검토 |
| NFR-004 | 사용성·호환성 | 시스템은 목표 브라우저에서 검색·상세·비교 흐름을 완료할 수 있어야 한다. | Must | 팀이 기록한 Chrome·Edge 버전에서 수동 확인 |
| NFR-005 | 유지보수성 | 시스템은 외부 데이터와 AI 제공자의 호출을 각각 독립된 어댑터로 분리해야 한다. | Must | 대체 응답을 주입해 검색·추천 로직 검증 가능 |

응답시간의 정량 목표와 평가 환경은 프로토타입 측정 후 합의한다. 아직 측정하지 않은 성능 수치를 달성했다고 기재하지 않는다.

## AI 요구사항

| ID | 요구사항 | 검증 기준 |
|---|---|---|
| AI-REQ-01 | 시스템은 LLM이 추출한 조건을 허용된 스키마와 값으로 검증한 후 검색에 사용해야 한다. | 잘못된 JSON·미지원 필드·역전 날짜에서 보정 또는 재질문 |
| AI-REQ-02 | 시스템은 프로그램 사실과 추천 근거를 실제 검색 결과에 한정하고 확인되지 않은 값을 생성하지 않아야 한다. | 결과 밖의 프로그램 ID·날짜·신청 링크가 응답에 포함되지 않음 |
| AI-REQ-03 | 시스템은 AI 오류 시 확정되지 않은 답변을 표시하지 않고 재시도 또는 입력 수정을 안내해야 한다. | 모델 오류·비정상 응답에서 안내 확인 |

## 주요 화면

| 화면 | 목적 | 관련 요구사항 |
|---|---|---|
| UI-01 검색 | 질문 입력, 해석 조건 확인·수정 | FR-001, FR-006 |
| UI-02 결과·추천 | 후보 목록, 추천 이유, 미상 조건, 비교 선택 | FR-002, FR-003 |
| UI-03 상세 | 확인된 정보와 출처·수집 시점 | FR-005, FR-007 |
| UI-04 비교 | 2~3개 후보의 동일 항목 비교 | FR-004 |

와이어프레임은 팀원 2·3이 화면 흐름과 함께 보완한다. 현재 실제 화면은 없다.

## 데이터와 인수 기준

데이터 항목과 이용조건은 [API 검증 기록](data-api-review.md)을 따른다. 프로그램별 링크·비용·주소는 실제 제공될 때만 사용한다. 수집 시점과 원천 갱신 시점은 구분한다.

| ID | 인수 기준 | 관련 요구사항 |
|---|---|---|
| AC-001 | 합의한 질문 세트에서 조건 추출 후 실제 후보를 확인할 수 있다. | FR-001, FR-002 |
| AC-002 | 추천 이유의 각 조건이 데이터 또는 명시된 파생 규칙으로 설명된다. | FR-003, AI-REQ-02 |
| AC-003 | 선택한 2~3개 프로그램의 확인된 값을 비교할 수 있다. | FR-004 |
| AC-004 | 상세 화면에서 출처와 수집 시점을 확인한다. | FR-005 |
| AC-005 | 결과 없음·누락값·외부 장애에서 임의 사실을 생성하지 않는다. | FR-006, FR-007, NFR-001, AI-REQ-03 |

추적표는 [테스트 계획](test-plan.md)에 있다. 승인란은 실제 검토자의 확인 후 제출본에 작성한다.
